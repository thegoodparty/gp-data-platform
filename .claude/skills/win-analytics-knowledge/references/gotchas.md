# Known gotchas reference

Part of the **win-analytics-knowledge** skill. Recurring traps, as a quick-reference symptom table.

## Quick reference

- **What this is:** a symptom → mitigation index. When a trap is fully explained by its home doc (joins, outcomes, viability, etc.), this table carries the **symptom** and points there rather than restating the fact — so a fact lives in exactly one place.
- **How to use it:** scan the Symptom column for what you're seeing, then follow the mitigation's link for the full explanation.
- **Maintenance:** when you hit a new trap, add a one-liner here; put the full explanation in the owning domain doc.

## Reading the Status column — these are not all permanent

Each entry is tagged:

- **`invariant`** — a methodological or structural truth that does not drift (a statistical fact, a data-model property, a policy). Trust it.
- **`state · as-of YYYY-MM`** — a data- or code-state fact with a shelf life. Treat it as a **hypothesis to re-verify against the live catalog**, not a standing truth — the older the as-of date, the more suspect. Some are designed to become false (e.g. a "fix ticketed" trap flips once the fix ships). The as-of date is the last point the fact was confirmed; the owning domain doc carries the fuller dated context.

The as-of dates are at month granularity on purpose (no false precision). State entries are re-verified by hand at each consolidation pass (dated at the top of `analytics/runbook/CANDIDATES.md`); a state row whose as-of date is more than a quarter older than the last pass is due for a check.

## Gotchas

| Gotcha | Symptom | Mitigation | Status |
|---|---|---|---|
| **`users_win_base.election_date = coalesce(next, last)`** | Leaks future election dates into "current cycle" analyses. | Use per-stage dates from `users_win_candidacy` instead. They are NOT coalesced and preserve cycle separation. | invariant (model definition) |
| **Corrupt election-date values (out-of-range years; all per-stage date columns)** | A handful of latest-version non-demo rows (17 as of 2026-06) carry out-of-range years like `+275760`, `+20021`, `0024` — seen on `election_date` and on `general_election_date` (`+202407`, 2026-07); the far-future ones pollute `MAX(election_date)` so those users read as perpetually upcoming — inflating any "election on/after date D" base — and they crash the non-arrow connector's date parser on return. | When aggregating **any per-stage date column** (`election_date`, `primary_election_date`, `general_election_date`, runoff dates), bound to a sane window: `MAX(CASE WHEN <col> BETWEEN DATE'2020-01-01' AND DATE'2050-01-01' THEN <col> END)`. Return dates as STRING if corrupt rows can reach the client. Base recipe in [segmentation.md](segmentation.md). | invariant (principle); count illustrative · 2026-07 |
| **`candidacy_result` cross-stage fallback** | A primary winner who lost the general can show `candidacy_result = 'Won'`. | Use `latest_stage_result` + `latest_stage_reached` (or `general_election_result`). See [outcomes.md](outcomes.md). | state · 2026-10 |
| **Viability read from the wrong mart** | Coverage looks ~1% when it should be 60%+. | Read `candidacy_scored`; `candidacy.viability_score` is the archive-only gap-filler. See [viability.md](viability.md). | state · 2026-08 |
| **Viability scores shift between builds** | Same query, different scores later. | Scorer loads latest MLflow versions + mutable WoE lookups; record `model_version` from the scoring intermediate; pin analyses to a snapshot date. | invariant |
| **Pre-2025-05-28 candidates have no Win-product Amplitude history** | Earlier `users.created_at` rows exist in the product DB but have no Win-Amplitude events (instrumentation went live ~2025-05-28; see [engagement.md](engagement.md)). | For engagement-window floors, use the **actual coverage `MIN(week_start_date)`** of the source table, not a fixed date. Document the coverage window in the brief's `data_provenance` field. | state · 2026-05 |
| **NULL `election_level` is a large bucket** | Office-level slicing loses a third to a half of the population if you filter (45.6% NULL in 2026-05, 36.6% in 2026-10). | Decide explicitly: (a) restrict, (b) backfill from `office_type` / `int__icp_offices`, or (c) treat NULL as a fifth category. See [segmentation.md](segmentation.md). | invariant (principle); figure illustrative · 2026-10 |
| **Pro users have LOWER raw win rate than free** | Naive Pro-lift analysis flips intuition. | Confounded by selection bias (Pro users self-select into harder races) and reverse causation (engagement → Pro). Office-stratify; use pre/post-upgrade frame for timing. | invariant (mechanism); direction measured 2026-05 |
| **ICP=true cohort has LOWER raw win rate than ICP=false** | Same direction as the Pro finding. | ICP=true offices are by-design competitive. Slice rather than filter. See [segmentation.md](segmentation.md). | invariant (mechanism); direction and figures in segmentation.md, measured 2026-05 |
| **2025 archive vs 2026+ FOJ structural mismatch** | Field availability differs (e.g., `is_open_seat` absent from 2025 archive). | Slice by `source_systems` and `year(general_election_date)` together. Don't pool blindly. See [sources.md](sources.md). | invariant (model structure) |
| **Outcome data concentrated in 2025** | 2026 outcome coverage was <10% in 2026-05 and 19% in 2026-10, still far below 2025. | Name the cycle your outcome labels come from; "did they win" analyses stay mostly a 2025 study until the 2026 generals report. | invariant (principle); figures illustrative · 2026-10 |
| **`votes_received` is STRING** | Casting fails on rows containing "uncontested". | Filter or coalesce the literal before casting. See [outcomes.md](outcomes.md). | invariant (documented column contract) |
| **Multi-cycle candidates** | One user can produce multiple `campaign_version_id` rows. | Filter to `is_latest_version` for the canonical row; collapse cycles explicitly. See [joins.md](joins.md). | invariant |
| **Amplitude self-reported outcome response bias** | 80% self-report "won" vs 64% raw population win rate. | Use labels, NOT rates. See [outcomes.md](outcomes.md). | invariant (principle); figures illustrative · 2026-05, detail in outcomes.md |
| **L2 PII boundary** | Voter-grain L2 models carry PII-adjacent records. | Aggregate-grain queries only by default. See [sources.md](sources.md). | invariant |
| **Mart staleness vs SQL state** | Prod mart may carry data the current SQL doesn't produce (e.g., viability). | When code/data disagree, trust the data for current state but flag the discrepancy. Don't extrapolate forward. | invariant |
| **`users_win_candidacy.hubspot_id` is the COMPANY id, not the contact id** | Joining `stg_airbyte_source__hubspot_api_feedback_submissions.hs_contact_id` directly to `users_win_candidacy.hubspot_id` returns zero matches. | Use the 2-hop via candidate. See [joins.md](joins.md). | state · 2026-10 |

| **Onboarding milestone flags are new-flow-blind** | `onboarding_complete` / `has_completed_onboarding_flow` / `is_onboarded` / `int__user_product_activity.is_onboarded` / the lib `onboarded` flag read FALSE for post-cutover users, so a cross-cutover analysis shows a fake completion collapse. | Recompute **onboarding dashboard viewed** (broad) or the era-resolved pledge union (strict; 3 events — `Onboarding - Candidate Pledge Completed` alone is V2-era-blind, dead after 2026-06-10). Mechanism, dates, and verified wrong-reads are in [engagement.md](engagement.md). | state · 2026-10 (re-verified in SQL; no fix ticket exists, DATA-1947 was the analysis and is closed) |
| **Dashboard-view surface gets renamed** | Any metric anchored on a *named* dashboard event silently zeroes when the product rebuilds the surface (three times so far: 2026-06-13, 2026-07-31, successor from 2026-08-07). | Read the legs from `win_active_candidates_30d`'s `config.meta.anchored_on` (path-anchored on `/dashboard` since DATA-2337) and check instrument liveness via the omni lifecycle assets before trusting any standing definition. Timeline in [engagement.md](engagement.md). | invariant |
| **Account-creation column name** | `users_win_base.user_created_at` does NOT exist. | Account creation = `users_win_candidacy.user_created_at` (= `users_win_base.registered_at`, byte-identical). | state · 2026-10 |
| **Civics classification lag on recent signups** | Recent registrants carry NULL `election_level` / `office_type = 'Other'` until the civics mart classifies them, so office/level cuts on a recent cohort collapse. | Treat office/level stratification as a structural finding on the older classified cohort; don't read a recent pre/post office cut. | invariant (principle); as-of 2026-05 |
| **Amplitude coverage can lead the calendar date** | `MAX(event_time)` may be ahead of "today" (e.g. 2026-06-06 seen on 2026-06-02). | Compute `data_max = MAX(event_time)` live and derive censoring cutoffs from it; never hardcode "today" or a stale max. | invariant |
| **Closed-cohort retention declines by construction** | An election- or signup-anchored closed cohort (membership fixed by first-active week) decays toward the anchor the way any weekly retention does, and gets misread as the base disengaging as the election nears; an election-anchored activity share likewise ramps because users *arrive* near their election and collapses at the observation edge. | Pair any closed curve with an **open fixed-denominator** view (numerator = users active that week, denominator = full population held constant), then split open into **new** vs **returning**; the returning line is the reverse-retention read. Condition activity-curve denominators on signup and on fully-observed weeks. Win figures and reference builds in [engagement.md](engagement.md), Retention curves. | invariant |
| **Moving or eligibility-filtered denominator makes a rate trend a composition artifact** | A cross-period rate's level AND trend move even if no individual user's behavior changed, because the denominator's composition is shifting. Mechanisms seen on Win: a cumulative-stock denominator against a signup-windowed numerator (old registrants' window closed, possibly pre-instrumentation, depressing the level; recent registrants right-censored, and the censored share varies by period, biasing the trend); a declining pre-instrumentation structural-zero share mechanically lifting the rate; upcoming-election eligibility churn. | **Hold the cohort/denominator fixed and re-measure; if the trend flattens, it was composition, not behavior.** To equalize windows: restrict the denominator to users whose full N-day window closed by the cut (signup ≤ cut − N days), or report the censored/ineligible N separately. The dual of the closed-cohort row above: that one is fixed membership decaying; this one is moving membership shifting. | invariant |
| **Partial-coverage civics fields carry a channel signal in their missingness** | `contested` is unknown for 71% of self-signups against 7% of roster rows, and the unknown bucket carries the *highest* touch rate (45.9%). Pooled discrimination over the three-level field (touch AUC 0.663) is therefore mostly "does any source know this race": the unknown flag alone reaches 0.635, known rows only 0.581. Incumbency has a milder version (21% vs 3% unknown, unknownness alone 0.551). The power target is unaffected. | Check missingness-by-channel before ranking any partial-coverage civics field, and report known-rows-only alongside the pooled figure. Signup channel itself is in [segmentation.md](segmentation.md). Reference: `predictor_ranking.py` diagnostics (DATA-2247). | state · 2026-08 |
| **`is_uncontested` is rolled to candidacy grain across election stages** | A candidacy counts uncontested if it was uncontested at *any* stage, so a primary walkover followed by a real general reads as uncontested. 636 rows flagged uncontested carry at least one opponent and 11 carry ten. | The rollup is in analysis code (`win_power_users.py:424`, `MAX(CASE WHEN is_uncontested ...)`), not in the mart. Restricting to rows where the flag and `n_opp` agree widens the engagement gap from 2.4x to 6.1x, so the defect **attenuates** and any published contested effect is conservative. Second sighting of stage-grain rollup semantics after the TS-vs-stage disagreement recorded in the ledger (2026-08-14), and in the opposite direction. Verified against `n_opp` in `dimension_challenge.py` (DATA-2368). | state · 2026-08 |
| **Conditioning on ICP is range restriction on `voter_band`** | The Win ICP gate contains a district-size rule (500 to 100,000 voters), so inside the gate district size is jointly non-null at only p=0.052 with between-band spread 0.096, and every band reads as composition. | The correct reading is **not** that district size is irrelevant, but that the gate already captures the signal and no refinement of it is supported: raising the floor to 1,000 is unsupported, since the 500-1,000 slice runs at 0.87 within self-signups against under-500's 0.28. Any district-size recommendation must state which side of the gate it lives on. DATA-2154 would change the gate's contents. | state · 2026-08 |
| **Activation counts legacy self-reports tagged `method = 'unknown'`** | `is_activated` reads higher than the rule allows; many "activated" users are not Pro and have no product-DB send. | Exclude `method = 'unknown'` alongside `manual` until the semantic-layer anchor is widened; 340 of 1,307 activated users (2026-10-01) rest on it alone. Mechanism in [engagement.md](engagement.md). | state · 2026-10 (fix pending metric owner) |
| **"In the civics mart" is not a BallotReady match** | Only ~26% of a live Win cohort has a `mart_civics.candidacy` row, and any match rate conditioned on having one reads 70-80%. | The product leg admits a campaign only once ER clustered it with a vendor record or HubSpot verified it, so mart presence is the match output. Measure matches on the ER clusters or an in-race name match; derive filing deadlines from the signup race, not the person match. Recipe in [joins.md](joins.md). | invariant |
